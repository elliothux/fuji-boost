## 2026-10-28：XP4 外设接线与电源 SPI 协议修正

本轮从固定 FujiMod catalog 生成 `profiles/boards/xt4-212.generated.json`，接入 GPIO、ADC、温度、定时器、SPI、电源 peer、显示/成像、解压与 SD clock 模型。每份输入的 SHA-256 与未验证假设记录在同目录 `provenance.generated.json`。这些是声明的模拟环境输入，不是机身实测数据；Flash/DMA 介质布局、SD 卡与 USB 尚未接入。网页默认严格模式保持不变。

实际修复了一处协议选择错误：X-T4 loader 的读命令为四字节 `(reg & 0x7f), 0, 0, ~reg`，写命令为 `reg|0x80, high, low, checksum`，四字节之和为 `0xff`。catalog 原先选用的三字节 PowerSerial 在第 57,642 条指令把 `00 00 00 ff` 的第四字节误判为 register63 写入。现在复用上游 ChecksumPowerSerial；不再把原三字节 peer 的 RTC 语义套到这个 loader 上。

**分开保留三类结果：**

- 默认严格网页/native/Wasm：7,346 条指令后仍拒绝未知 `0xfff4a400`；没有 shadow 干预或电源输入覆盖，native/Wasm 四核寄存器、配置哈希、停止原因一致。此结果仅证明有边界的局部执行。
- 诊断 + catalog `reg0=0`：修正校验协议后执行了 20,000,000 条预算指令，持续停留在电源状态轮询，未进入 ThreadX/相机 UI。历史快照：status-zero。
- 诊断 + 明确输入 `reg0=0x8000`：通过 loader 对高字节符号位的检查，执行到 191,598 条指令，停止于 `Unsupported checksum power SPI write register17 value0x7f00`。报告：ready probe。这是合成输入探针，包含 discovery 的影子访问和 poll-bit 干预，`bootVerified` 始终为 false，不能算完整开机。

同一份实际 loader 还确认：`0xfff48700` 是 SPI configure 的 selector 写入，公式为 `selector << (channel*2)`，SPI1/selector1 对应写值4。物理时钟/路由含义尚不明确；不能直接照搬别的 Milbeaut 芯片寄存器。电源 `reg17=0x7f00` 的硬件副作用，以及候选保留寄存器31..34的断电行为也未证实。REA/Hopper Evidence 与独立指令/校验验证 已留存，`verify.py` 通过。

新增 `bun run research:xt4` 与 `bun run research:xt4:ready` 作为仅限原生的诊断命令，浏览器没有 permissive/discovery 开关。 完成条件逐项核对见 目标审计，完整启动一项仍为未实现。生成器与 Rust 的重载路径已接线；生成文件不应手改。`bun run check` 现同时检查固件核心与 XP4 桥接的 Clippy。 新版 native/Wasm 一致性、浏览器实际加载/严格执行和默认单元测试均通过；截图：当前严格运行。另已将 `research/` 排除在 Vite 监听之外，防止保存研究 HTML 时重置模拟会话。

公开硬件资料另找到 R5F100EDA 系统 MCU 候选，但尚未确认它就是 SPI peer。官方 RL78/G13 内存布局不能证明 DAT 内含其固件；MAX77812 的四字节 SPI 格式与此协议不匹配，不能直接套用其寄存器表。[硬件资料与搜索边界](../../../research/xt4-board/hardware-docs/ASSESSMENT.md) 已保存。现有 DAT/四段映像的 ASCII 搜索没有识别出有效 MCU 标识，宽松向量表筛选返回大量数据误匹配，不能据此确认或排除 MCU 固件；见 MCU 候选检查。

**剩余条件：** 默认严格启动仍需要两个全局控制寄存器的可靠行为模型、匹配的电源命令语义，以及 Flash/DMA 等介质接线。现有结果没有 LCD 菜单、拍摄、蓝牙或 Wi-Fi 成功证据，完整目标继续保持未完成。

## 2026-10-28：有限电源命令与无有效保留数据场景

在实际 loader 与两段主映像的调用路径中，电源寄存器17的高字节初始化命令与低两位请求可区分。`0x7f00` / `0x3700` 是观察到的常量，但缺少写后状态变化闭环，不能声称已证明 W1C。详见 主映像调用与证据边界。

已将有限命令接口实现为显式选择的原生诊断模型：状态16固定为0时，只记录并应答两条高字节命令；低两位电源转换请求记录后停止，其他值拒绝，日志上限256条。浏览器默认构造器不启用该模型。电源相关的上游四处源码变更保存在 `patches/fujimod-power-commands.patch`，与独立 Flash 补丁按顺序由setup/build幂等应用并拒绝冲突；补丁验证 确认干净应用与当前源码逐字节一致、重复应用不改动源码。

- `bun run research:xt4:commands`：到225,174条指令，记录 `reg17=0x7f00` 后停在未支持的 `read reg31`；报告。
- loader 将寄存器31–34读成8字节，以第6字节 `0xaa` 标记和第7字节负和校验判断有效性。新增 `bun run research:xt4:retained`，仅在本次会话中用四个初始全零的16位存储字模拟“没有有效保留数据”。不提供 RTC、reg39提交或断电保持语义。
- 该场景完成3,000,000条预算，未发生CPU failure，仍停留在 loader；core0在 `0xfffd8040` 轮询，记录127条 frontier 和43次 discovery 干预。报告。无 failure 仅说明该预算内没有拒绝，不证明启动成功。
- `bun run test:xt4:scenarios` 用实际 DAT 执行100万条预算，核对四个真实 SPI 读帧、RAM `0x10c30` 有效标志为0和八字节数据全零；测试通过。电源 peer 的7项聚焦单元测试也通过，包含默认拒绝、校验和、无效命令与 checkpoint 校验。

上述诊断都报告假设、输入覆盖和 discovery 干预，`bootVerified` 始终为false。完整启动仍未完成；下一关是 Flash 控制器/传输与介质布局的可验证模型，不能靠继续自动翻转未知状态位宣称跑通。默认严格模式还需解决已有 I/O gate 与 selector 的真实行为。

## 2026-10-28：SMP 到达标记覆盖与原厂主入口执行

4项实际DAT场景回归测试已通过，新增测试确认次核在primary初始化阶段没有运行、随后guest自行解除屏障并执行真实主入口。该结果不是完整开机或UI验收。

## 2026-10-28：GPIO 启动输入与有界启动原因，下一关 reg39

被动Wasm轨迹把原厂 `0x01291818` 停止分支归因到实际输入，而非CPU故障：初始GPIO bank0=3由原始loader采样并复制到handoff，main在 `0x012913c8` 读bit0返回1，启动判断返回0。显式把模拟外部输入3改成2后，原厂采样值自然成为2、GPIO helper返回0；但保存的启动原因仍为0，之后retained deadline gate也自然返回0。两次guest预加载补丁完全相同，没有改handoff、PC或返回值。双轨迹校验、来源/分支、无启动原因的闭环。低电平不等于已识别某个实体按钮。

新增累计预加载场景明确声明一次初始电源status16=0010。实际loader在17初始化命令之前读16，将它映射成保存的启动flag4；main随后自然走早期启动分支，`0x01291384` 与 `0x012917e4` 的R0均为1。该值也对应catalog历史声明的cold reason4，但现在通过原始输入/采样路径产生，而非直接覆盖handoff。实际cause轨迹、核验。

没有把17=7f00猜作已证实W1C：checksum初始化命令仅被记录和应答，随后16的状态标成unknown，任何再次read16都会明确拒绝。新增聚焦测试验证初始化前读取、坏校验不改变状态、正确命令后拒绝读16、checkpoint恢复与非法cause输入；共9项电源peer测试通过。默认严格模式和旧zero-status场景均保留；原生 `--inactive-countdown` / `--startup-input` 可复现前两层实验。

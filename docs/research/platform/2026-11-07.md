## 自定义固件 + PocketJS 在模拟器内先行的可行性评估

用户下一步计划：实现自定义固件，把 [pocket-nexus/pocketjs](https://github.com/pocket-nexus/pocketjs) 移植过来，先在模拟器里跑通并使性能基本可用，为后续自定义 UI 与 App 铺路。本轮只做源码审阅与方案细化，没有编译、运行或改动产品代码。完整方案见 [docs/design/custom-firmware-pocketjs.md](../../design/custom-firmware-pocketjs.md)。

**判断：可行，建议按方案中的 M1–M5 推进。** 与 [日期未注明](undated.md) 的评估相比，这次的变化在于目标从"真机上寄生于原厂固件的扩展"改为"模拟器内独立的裸机固件"，而后者所依赖的条件全部已经在仓库内被源码或实测确认：

- 模拟器加载路径与原厂 DAT 解耦：`crates/xp4/src/lib.rs` 的 `prepare_inputs` 最终只是 `board.write(0, &ram)` 加四核 `PC=entry`；换成自定义映像不需要新的硬件模型。
- 显示、定时器、GIC、GPIO、ADC 的寄存器模型都在 FujiMod 源码中完整可读（`emulator-xp4-display/src/lcdc.rs`、`emulator-xp4-io/src/interval_timers.rs`、`emulator-ip/src/socionext/gpio.rs`、`emulator-xp4-io/src/adc.rs`），LCDC 支持 BGRA8888 平面与 Q12 最近邻放大，两路相位 IRQ 可作 vsync。
- 板级对 WFI 核心做时间跳过，单核固件可独占宿主吞吐。
- PocketJS 固定提交 `e27bff3` 具备 `no_std` core、带 `bare-platform/software-only/host-allocator` 的 C ABI staticlib、便携 QuickJS 胶水，以及 GBA（无 OS ARM）、ESP-IDF（脏矩形软件渲染）、PSP（单 arena）三个可直接参考的 host。

## 性能数量级（实测基线，非承诺）

| 来源 | 数据 |
| --- | --- |
| `.cache/xt4-tests/endurance.json` | 31,386M 指令 / 120 guest 秒 / 319.4 wall 秒 → 98 MIPS |
| `.cache/opt15/acceptance-results/endurance.json` | 29,794M 指令 / 120 guest 秒 / 225.1 wall 秒 → 132 MIPS |
| `.cache/opt13/REPORT.md` | 串行 REC 100M 指令 1.119 s → 89 MIPS |

以 profile 的 1 指令/tick、54 MHz 计，30 Hz guest 帧预算为 1.8M 指令；在 ~100 MIPS 宿主上约 18 ms，因此"每帧 ≤ 1.8M 指令"是模拟器内接近 30 fps wall 的工程门槛。PocketJS 在 PSP（333 MHz）上报告的 2.2–3.6 ms JS 每帧与 ESP32-S3 host 的存在支持这个数量级可达，但本轮没有在 ARM/TCG 上实测，浮点在 TCG 下的开销是首个要测的未知。方案把验收写成可测数字：启动 ≤ 1.0G 指令，静止帧 ≤ 0.3M，交互帧 p95 ≤ 2.0M，宿主静止 ≥ 30 fps、交互 ≥ 20 fps，120 guest 秒无未建模访问。

## 模型事实勘误与约束（写入方案时核对）

- LCDC 像素时钟由 `ticks_per_pixel=2` 固定为 27 MHz，900×600 在模型内做不到 60 Hz，极小消隐时上限约 49 Hz；方案按 30 Hz 设计。
- LCDC 图片平面要求 `+0x40/+0x44` 与 `+0x48/+0x4c` 相等、`+0x50` 高位恰为 `0x10000`、`dx/dy` 非零且 `((w-1)*dx)>>12 < sw`；越界即 CPU 停止。
- ADC 模型基址为 `0xfff40000`，不在 `io_group_base` 之下；GIC 只解码 `CBAR+0x1000..0x3000`。
- 蓝牙 UART 模型只计数不保存字节，固件日志改用 RAM 环 + `read_physical_memory`。
- 真机第 0 页未映射，映像基址避开 0。

## 未知与边界

- 真机路径（X-T4 SD_BOOT、DDR 初始化、电源 MCU 握手、面板初始化）仍未验证，方案只以 HAL 分层为将来保留接口，不作承诺。
- quickjs-ng 在 newlib-nano 裸机上的 libc 缺口、Rust 自定义 target 与 PocketJS 固定 nightly 的兼容性、TCG 浮点性能，均需 M1–M3 实测后在本领域追加记录。
- 本机尚无 `arm-none-eabi-gcc`；M1 第一步安装。

## 实现记录：M0–M5（同日）

按 [方案](../../design/custom-firmware-pocketjs.md) 实现了裸机固件 `firmware/`、模拟器侧 `CustomSession`、`xt4-camera` 自定义命令和网页 `?custom` 页面。PocketJS 计数器与"胶片配方"仪表盘两个 TSX 应用在现有 XP4 模拟器（FujiMod board + Unicorn，严格 MMIO）中启动、响应按键、热重载，§6 的验收数字全部达标。全部数字来自 `bun run test:xt4:custom`（8 个 ignored 测试，约 38 s）与网页实测，证据在 `.cache/custom-firmware/`。没有连接或刷写实体相机。

### 与方案不同的决定

- **工具链**：没有安装 `arm-none-eabi-gcc`/newlib。C 侧用 Homebrew `llvm@19` 的 clang（经 `cc` crate），链接用 rustc 自带的 lld，libc 是 `firmware/libc/` 里约 1.3k 行（含头文件）的最小实现（malloc 走 64 MiB arena、字符串、`snprintf` 数字格式、math、`setjmp` 头）。Rust 用 `nightly-2026-10-10` 与内置 `armv7a-none-eabihf` 加 `-C target-cpu=cortex-a7` 和 `build-std`，不需要自定义 target JSON。
- **QuickJS**：PocketJS 固定提交实际使用 Bellard QuickJS（`pocket-nexus/quickjs-rs` `ba5bdd0`，与其 Symbian 工具链同一版本），不是 quickjs-ng。`bun run setup` 现在会把 pocketjs `e27bff3` 与 quickjs-rs `ba5bdd0` 固定拉到 `references/`。
- **ui-cabi**：只开 `software-only`。它的 no_std 路径自带基于 C `malloc` 的全局分配器与 panic handler，固件需要 `extern crate pocketjs_symbian_core` 才会链接进来。
- **target 注册**：不给 PocketJS 打补丁。`firmware/app/profile.ts` 仿照其 `iphone2g-dev` 在仓库外定义 `fuji-xt4`（takeover、450×300 原生、density 1、`input.buttons`、`text.glyphs.baked`），由 `firmware/build.ts` 解析 manifest 后调用 PocketJS `tools/build.ts`。
- **显示**：§3.6 方案 A 保持为默认，即 450×300 逻辑面由 LCDC1 Q12 放大 2×。帧循环把 damage 行复制到单一 present 缓冲，复制发生在 IRQ 118（捕获完成）之后，所以不需要双缓冲翻页。方案 B 没有实测：选中帧的渲染已占 1.3M ticks，4× 像素会让交互帧超预算。

### 模型事实（方案勘误）

- 间隔定时器在 profile `timer_base` `0xfff3c300`（0x50 字节窗），不是 `0xfff38000`。固件把通道 7 当自由运行的递减计数器（IRQ 不开），计数由虚拟 tick 推导，可作 54 MHz 时钟。
- LCDC 相位脉冲必须在 GIC `ICFGR` 配为边沿触发。按电平配置时，脉冲落下后 pending 位随之消失，WFI 永远等不到。
- 启动期（85M ticks）里 IRQ 118 的边沿会一直锁存，`gic::wait` 立刻返回这个陈旧边沿，帧相位因此随机，帧循环把每次捕获都判成迟到，第一次 pocket 测试跑了 15 分钟。修正是先 `gic::discard`，再等一次新的捕获，再把相位原点设在其前 `FRAME_TICKS/16`。热重载之后同样重新锚定。
- `JS_Eval` 要求源码以 NUL 结尾。应用槽复制和内嵌 bundle（`Terminated<N>`）都多带一个 0 字节，否则热重载报 `SyntaxError: unexpected end of string`。
- PocketJS 没有初始焦点时，OK 键不会派发到按钮。应用根节点用 `FocusScope`（autoFocus）。
- 宿主侧每次 LCDC 捕获约 3.5 ms：hello 固件几乎不执行指令，120 guest 秒用了 13.1 wall 秒。这是空闲帧的宿主下限（约 280 fps），不是固件开销。

### §6 验收（模拟器，Apple Silicon 原生服务端）

| 指标 | 目标 | 实测 |
| --- | --- | --- |
| 启动到首个 PocketJS 帧 | ≤ 1.0G 指令，宿主 ≤ 10 s | 计数器 88.1M 指令（runtime boot 85.3M ticks，guest 1.64 s），宿主 0.55 s；仪表盘 boot 98.5M |
| 静止帧 | ≤ 0.3M 指令 | 78.9K（4.4% 帧预算） |
| 交互帧 p95（仪表盘 120 s 脚本：焦点移动、选中、每 2 帧动画、每秒文本） | ≤ 2.0M | p50 664K、p95 678K（37.7%）、p99 969K |
| 宿主帧率 | 静止 ≥ 30、交互 ≥ 20 fps | 不限速 206–227 fps（实时 6.9–7.6×）；网页限速 30 fps、实时 100% |
| 内存 | 堆 ≤ 8 MiB，arena 峰值 ≤ 32 MiB | 仪表盘峰值 2.59 MB；两次热重载（计数器→仪表盘→计数器）后在用 2.79 MB、峰值 3.58 MB。比内嵌启动多出的 0.69 MB 正好是从应用槽复制的计数器 js+pak（683 KB） |
| 稳定性 | 120 guest 秒无 `cpu.failure`、无 JS 异常 | 通过；missed vsync 0 |
| 确定性 | 两次运行帧哈希一致 | 通过；checkpoint（4.1 MB）恢复后执行同一段输入，画面与邮箱和原会话一致 |
| 开发闭环（M5） | 改 TSX 到看到画面 ≤ 5 s，不重链固件 | 3.64 s：重打包与网页 1 s 轮询共 1.64 s，guest 按实时重启 2.0 s |

已知超预算：选中配方的那一帧约 2.7M ticks（JS 1.4M、渲染 1.3M），会重复显示一帧。原因是几处 damage 矩形取并集后接近全屏。应用切换后的首帧约 4.6M ticks。测试的门槛是每次选中最多超预算一帧，超出的帧小于 2× 预算，且不丢捕获。模拟器按 1 指令/tick、54 MHz 计时，比真机 A7 悲观。

### 调优与 A/B

- 稳定帧 PC 采样（`bun run firmware:profile`）：QuickJS 65%（`JS_CallInternal` 约 48%），ui-cabi 26%。选中帧里 ui-cabi 占 48%，其中 `render_scaled_clipped` 占 24%。
- 原先 `compiler_builtins` 的弱 `memcmp` 是逐字节循环，占稳定帧采样 11%；用 `firmware/libc` 的按字比较版本覆盖后降到 4.6%。
- 关闭 NaN boxing：p50 722K、堆 2.70 MB，两项都更差，所以保留默认的 NaN boxing。
- C 用 `-O3`：p50 658K（约 1%），映像增大 43 KB，保留 `-O2`。

## 补充：模拟器与固件解耦，统一相机页（同日）

`?custom` 独立页面已删除，自定义固件改为统一相机页上的预设（`?firmware=fuji-boost/pocket`、`fuji-boost/hello`）。模拟器侧的 `CustomSession` 换成与固件无关的 `ImageSession`（`crates/xp4/src/ram_image.rs`），它只做映像加载、执行、输入、LCD、内存读写和 checkpoint。日志环、状态字和应用槽的约定只在 `firmware/protocol.json` 写一次：`firmware/build.rs` 生成固件常量，`firmware/build.ts` 把协议、映像加载地址/入口和应用索引写进 `firmware/dist/fuji-boost.json`。网页（`src/lib/firmware-presets.ts`、`src/firmware-debug.tsx`）和 `crates/xp4/tests/custom.rs` 都从清单读取布局。服务端去掉了 `load-app`、`custom-log`、`custom-checkpoint`、`custom-restore`，热重载只用通用的 `write-memory`。

### 事实

- **按 guest 时间推进需要专门的调度。** 网页改为每次请求推进 1/60 s guest 时间，不再"推进 1 帧"，因为后者依赖固件的帧语义。直接调用 `run_board(budget)` 会越过目标：busy 批次的指令数与剩余 tick 无关，hello 从启动转入空闲那一段，一次请求越过了几百帧。把批次速率存在会话里还会让 checkpoint 恢复后的停点不同。`ImageSession::run_for` 改为自己轮转可运行核心：单核可运行时每批 1M 指令，多核时 1024；每批再截到剩余 tick；全部等待时调用 `idle()` 跳到下一个事件，跳过目标后立即返回。停点只取决于 guest 状态。
- **新调度下的测试数字**：8 个测试全部通过。仪表盘耐久 120.0 guest 秒、3600 帧，wall 15.1 s（实时 8×），交互帧 p95 678,082、静止帧 78,884。启动到首帧 88,144,232 指令，帧 SHA 与黄金图一致。hello 耐久正好 3600 个 vsync。测试内应用槽热重载 wall 457 ms。
- **网页实测**（`camera:native` 原生服务端，Apple Silicon）：PocketJS 实时 101%，按两次 OK 计数为 2；点"dashboard"热重载 0.01 s 见画面；`firmware:app` 监听下改 TSX 后自动重载到第 2 代应用。hello 实时 100%，方向键移动方块，OK 换色。切回原厂预设，REC checkpoint 正常恢复，实时约 30%。
- **"Checkpoint device graph differs"**：用户截图里原厂页报了这个错误，用当前构建重启服务端后没有复现。原厂预设与映像预设来回切换后，REC checkpoint 都能恢复。推测当时浏览器连到的是 board 设备图不同的旧服务端进程。没有找到能确定复现的步骤。

## 补充：自定义固件取景窗（同日）

用户要的是把宿主摄像头/图片接到 PocketJS 画面上，不是建模 XP4 imaging sensor，也不是打开原厂 MOVDC「画面源」。

- `firmware/protocol.json` 增加 `scene`：`0x0F020000`，16B 头 `FBSC` + generation/width/height，后面 RGB888，最大 450×300。generation 0 表示没有帧；宿主最后写 generation。
- 应用把取景窗涂成 `#010008`。软件光栅总是写不透明像素，不能靠透明挖洞。HAL 每帧把该色最近邻换成缩放后的宿主 RGB。新 generation 会强制整帧 damage，否则第一次 punch 之后像素不再是 chroma，画面会冻住。
- 网页在映像会话下把灰场/测试图合成 RGB 后走同一条 `scene` 命令（带 `address`/`generation`）。原厂 DAT 会话的 MOVDC 画面源不变。
- 这不是传感器/ISP；AE 统计也不走这条路径。
- **闪屏**：CleanShot `17.51.29` 可见取景窗在实景与近黑 chroma 之间撕裂（有时上半实景、下半黑）。原因是 present 先把 UI 的 chroma 拷进扫描缓冲再 punch；LCDC 在中间捕获就会扫到 key 色。改为 compose/refresh：按 UI 帧缓冲的 chroma 位直接写 scene，key 色不再进入 present。

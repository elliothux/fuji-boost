## 针对“保留原厂驱动 + 自研 dashboard/协议 + mobile App”的判断

**推荐把它设计成原厂固件上的扩展系统：先做 mobile App 和现有协议客户端，再针对确有必要的功能研究一个小型机内扩展。** 这在架构上成立，但 X-T4 上的机内扩展加载/运行仍是未验证前提。直接把已提取代码当作可链接驱动库、在自写 OS/UI 上调用，尚无依据：这些代码依赖原厂 RTOS、其他任务、启动状态、内存布局和共享数据，没有已知稳定 SDK/ABI。

推荐分层：

```text
自研 mobile App
  dashboard / 配方库 / 拍摄流程 / 预览
        ↕ 现有 BLE 与 Wi-Fi 应用协议（先实现手机侧）
原厂 X-T4 固件的通信与拍摄服务
        ↕
原厂 RTOS + 镜头/传感器/ISP/显示/存储/无线驱动

将来有必要时：在原厂固件内加入小扩展
  自定义命令 / 配方解析 / UI 叠加 / 色彩参数 hook
  复用原厂服务，加载入口和函数边界必须针对 2.12 实证
```

- Wi-Fi/蓝牙需要区分无线驱动、802.11/BLE 栈与应用消息。目标功能通常只要求实现手机侧的应用协议，无需重写射频/链路协议。若要新增机内 HTTP/自定义命令/GATT 服务，才需要机内执行入口和对应原厂网络接口；能在 App 端连接不代表可任意新增相机端服务。
- [libfuji](https://github.com/petabyt/libfuji) 已实现富士 USB/Wi-Fi/BLE 连接、legacy/secure BLE pairing、无线通信、tether 与 RAW conversion 模式，是手机侧协议实现的重要参考；每项具体操作在 X-T4 2.12 是否可用，仍要建立能力表。
- [fffw](https://github.com/tiredboffin/fffw) 列出 BLE 模拟 Camera Remote/XApp、触发拍摄、Wi-Fi handover、用户设置备份/恢复和 C1–C7 解析，且有 X-T4 配置记录。相关部分仍标为未发布，不能当成完整、现成、已对 X-T4 实测的导入 API。
- dashboard 在手机上可以先独立开发；dashboard 在相机屏幕上需要自定义代码执行、渲染与输入事件接入。首版适合保留原厂拍摄 UI，仅增加一个页面或叠加层；全面替换会连带原厂曝光/对焦/回放/录制状态机。

“胶片模拟导入”需明确三种不同能力：

| 能力 | 机内改动需求 | 可行性判断 |
|---|---|---|
| 导入现有模拟 + WB/高光/阴影等参数 recipe，保存到用户预设 | 若现有属性接口或备份恢复格式支持，可无需补丁；否则需少量扩展 | 最优先验证。App 存任意数量，按需同步到相机有限预设槽；不能先承诺所有参数可远程写 |
| 将自定义曲线/LUT 作用于相机 JPEG/EVF/视频 | 要定位成像处理路径、表格式与更新方式；可能需要机内 hook | 有研究价值但尚未证明。不能假设相机已有通用 `.cube`/LUT 加载器，且 JPEG/EVF/视频须分别验证 |
| 移植 Reala Ace 等新一代原厂算法 | 除 UI 外还可能涉及不同算法、ISP 与硬件依赖 | 本轮无 X-T4 可复现实现，不纳入首版承诺 |

App 自身处理照片、应用任意 LUT 是另一条可独立实现的功能，但不能称为已经改变相机直出或取景器画面。

最小产品验证顺序：配对/发现 → 读取状态与能力 → 遥控快门 → 验证可写参数 → recipe 单槽写入并读回对照 → 断连/重连后保留 → 验证实际 JPEG/RAW 元数据与照片结果。先读出并保存用户原设置，验证版本和字段范围，不把服务校准区当作用户设置。完成这个闭环之后，再根据已证实的协议缺口决定机内扩展范围。

## 相机机内自定义 UI：系统形态与具体技术路线

**系统形态。** “嵌入式软件”和“操作系统”并不互斥。X-T4 2.12 的实际固件包含 `ThreadX SMP/Cortex-A7/GNU` 标识，是带实时操作系统的嵌入式系统。ThreadX 负责线程调度、同步和通信；富士的拍摄、UI、存储、通信等代码在其上运行。不能把这说成有 Linux 桌面、Android 应用安装机制或已知第三方插件 SDK；也不能仅凭主固件标识把每个协处理器组件都归为同一系统。ThreadX 基本定位依据：[官方项目](https://github.com/eclipse-threadx/threadx)。

**现有 UI 线索。** 本地固定版本的 `fffw/ffun/ports/xt4/0212/task.h` 含 `TSK_UI`、`TSK_UILIB`、`TSK_LCDEVF`、`TSK_GRAPHIC`、`TSK_TOUCHPANEL`、`TSK_VGLIB`；`key_codes.h` 含 Q、Fn、拨轮、快门等事件标识；`ui.h` 含 UI 初始化、设置、取消、方向和参数事件。它们是作者逆向得到的标识，不是我们已定位并验证的函数接口。`openvg.h` 里的 EGL/OpenVG/OpenGL 枚举也不能单独证明可以直接调用那些 API。

**推荐实现：保留原厂运行系统，编译一小段与其 ABI 匹配的机内扩展，通过受控入口接入原有 UI/事件系统。** 具体工作顺序：

1. **恢复代码/数据映射。** 复用已解压内容，确认加载地址、入口、ARM/Thumb 状态、overlay、栈、可用 RAM 和多核归属。已有两段 inner header，但全图未完成。随后导入 Ghidra/Hopper，字符串用于找交叉引用，不能把字符串地址当作调用地址。
2. **定位最小原厂接口集。** 找到 UI 事件分派、绘制与刷新、设置读取、内存分配、消息队列/调度接口。记录每个候选的调用约定、参数结构、所有者任务和锁要求，再以调用者/被调用者证据校验。版本 2.12 的地址不能直接跨固件复用。
3. **证明自定义代码真正执行。** 优先研究现有服务/USB debug 能否在 X-T4 上提供合法的 RAM 读写和触发执行入口。读 RAM、写 RAM与让 CPU 执行是不同能力。`fffw/ff80` 有 debug RAM/key/commandline 实现供参考，但本轮未在 X-T4 验证。可能还需处理缓存一致性与安全上下文。开启 debug 可能涉及 EEPROM，不能称为完全无持久写入。
4. **做最小屏幕闭环。** 用匹配现有调用约定的 ARM 交叉编译器生成小型 C/汇编扩展。第一次仅做日志/计数验证；然后在正确 UI 上下文画一行 `FUJI BOOST`，再用一个按键切换并恢复。内存地址、栈和原指令必须可追溯；不假设已有 malloc/printf/动态链接器可直接使用。
5. **接入真实功能。** UI 回调将操作交给原厂设置/拍摄服务（通常需要原有消息/事件路径），不要直接改某个看似曝光/对焦值的内存变量。第一项可读功能适合显示已有 ISO/电量状态；第一项写功能只选已明确状态约束、可读回确认的设置。
6. **验证共存与退出。** 相机 UI/实时画面可能使用多个显示平面、双缓冲或重新绘制流程，直接写 framebuffer 可能一帧后就消失。应接入刷新周期或已有图形服务，保持原厂 UI 的所有权。检查半按、拍摄、录像、回放、菜单、LCD/EVF 切换、休眠/唤醒时扩展的进入、暂停和退出。不要阻塞高优先级拍摄任务。
7. **最后研究常驻加载。** 只有上述临时运行稳定、且 X-T4 的恢复链路明确后，再评估 SD 文件加载器或固件内补丁。SD 文件只有在已有 loader/入口会读取并执行时才有意义；“复制到卡里”本身不构成加载能力。固件内补丁需处理压缩大小、段布局、完整性、升级及恢复；现有 no-op roundtrip 没有验证这些修改路径。

最有信息量的机内里程碑是：**原厂拍摄系统继续工作，Fn/Q 中一个受控入口可显示并关闭一页自定义 UI，能够读出一项真实相机状态，重启后仍能正常启动。** 目前完成的是离线固件解码与重压基线；代码入口、原厂绘图调用和机上闭环均未打通。页面布局本身并非当前最大未知，入口和可调用服务才是。

## PocketJS 移植评估

用户提出 [pocket-nexus/pocketjs](https://github.com/pocket-nexus/pocketjs)。本轮审阅固定提交 `e27bff3e96df3c7b3c8263a34f2362b964df04fb` 的源码与平台契约，**它是合适的机内 UI 候选，但目前没有已确认的 X-T4/ThreadX 适配**。完整代码依据与适配清单见 [research/pocketjs/ASSESSMENT.md](../../../research/pocketjs/ASSESSMENT.md)。未安装依赖、构建或实机执行。

通用性补充：ThreadX 任务、队列、内存与生命周期 glue 可以复用；显示/输入/存储/Camera bridge 与加载入口需要设备或固件适配。相同 ThreadX 不提供统一硬件 API，也不保证 CPU ABI 或闭源固件内部地址一致。“支持 ThreadX”应理解为可复用源码层，而非通用可复制二进制。X-T4 首先应针对 2.12 打通，后续按实际重复部分整理通用层。

- `engine/core` 实际使用 Rust `no_std + alloc`，负责节点树、布局、字体/资源和 draw list，不要求 Linux/浏览器，也不直接依赖 QuickJS。
- `engine/ui-cabi` 提供 C staticlib；已有 `bare-platform`、`software-only`、`host-allocator` 路径。宿主可提供 alloc/realloc/free，但仍需匹配 ARM32 ABI、栈、对齐及失败行为。
- `engine/quickjs-c/pocket_runtime.c` 提供便携的 QuickJS/UI glue，可复用已有 UI HostOps 安装与逐帧处理。电脑构建 TS/TSX bundle，相机运行 QuickJS 和 native core。
- 已有 ESP-IDF 的 guest/binding/runner/software RGB565 结构可参考；runner 的 ESP-IDF API 不能直接在 ThreadX 上编译运行。Binding 将 JS 执行、渲染、present 和创建任务分开，对新 host 有利。
- 推荐只做一个 X-T4 host：单一 UI 拥有者、受控 heap、输入转换、软件渲染→富士 overlay 呈现、生命周期、窄范围 Camera bridge。相机端能力仍通过原厂服务调用实现。
- 先验证 native core 的文字/矩形可显示，再接 QuickJS bundle 与按键计数，随后读取真实 ISO；之后才接 recipe 写入、手机消息或长期加载。
- 主要控制/UI 可理解为 ThreadX 上协作的任务；它们多与系统静态链接，不能理解为已具备独立应用安装器。部分成像/编码依赖专用硬件或其他处理器。
- PocketJS 解决 UI 构建，不解决 X-T4 自定义代码入口、恢复链路、新胶片算法和无线驱动；项目 PSP 的内存/帧率测量不能直接作为相机性能承诺。MicroTS AOT 仍在开发，首版不以其取代完整 QuickJS 路线。

性能补充：PocketJS 作者在单核 333MHz PSP 上报告某个动画应用约 8MB，以及借助 PSP GE 的 480×272/60fps 游戏实例。这说明轻量 UI 有合理基础，不是最低配置或 X-T4 性能实测。我的判断是 X-T4 运行菜单/dashboard/配方列表很有希望；拍摄/录像并行时的 CPU 余量、连续空闲内存、显示格式/刷新路径仍未知。初版宜约 30fps、局部更新、少量烘焙资源，再测峰值 heap、GC/长帧和快门响应。示例 640×480 ARGB32 双缓冲为 2.344MiB，仅像素缓冲，不代表相机实际显示尺寸；完整分析见 `research/pocketjs/ASSESSMENT.md`，计算见 `research/pocketjs/performance-budget.json`。未在相机上运行或测速。

**值得折腾，且现在已经有实测可用的离线逆向入口；还没有足够证据把 X-T4 当作可以直接刷第三方固件的平台。**

这份 `FWUP0024.DAT` 精确匹配公开目录中的 **X-T4 2.12**。本轮实际解出 4 个 method-4 压缩段，共 **33,543,940 字节**；两个不同项目的 Rust/Go 解码输出相同；Go 重压的四段与原压缩段逐字节相同。保留其他字节、替换回这四段后，整个 DAT 与原件也逐字节相同。这说明原始文件的这些压缩段已经可以可靠地读取和无改动往返。

这不等于任意修改可用：尚未构造并验证修改后的容器校验、定位稳定补丁入口、证明机身接受和执行补丁，也没有 X-T4 已复现的完整恢复路径。本轮没有刷写、连接相机、操作服务模式或写校准数据。

如果想尽早获得实用功能，优先遥控/拍摄自动化/配方管理；如果兴趣是机内改造，优先 UI、按键、显示辅助这类边界相对小的目标，再考虑成像参数。新一代 AI 对焦、RAW 视频、新 codec 或超出传感器读出规格的能力，目前没有本轮证据支持。

## 功能可行性矩阵

“优先”是我基于现有接口与依赖作出的工程判断，不是承诺 X-T4 已实现。无需机内修改的路线与真正自定义固件分开：

| 方向 | 现实路径 / 现有基础 | 本轮判断与关键缺口 |
|---|---|---|
| 电脑/手机遥控、文件传输 | 官方 SDK 明列 X-T4；libfuji 的 USB/Wi-Fi/BLE | 最现实的第一类成果；具体功能、模式、固件兼容需逐项实测 |
| 条件触发、定时拍摄、曝光序列 | 外部程序用已支持的遥控操作组合 | 优先；延迟、稳定性和每个属性的可写性需测 |
| AE/ISO/WB/DR/胶片包围 | X-T4 已有原生包围功能 | 先利用原生能力；自定义顺序/更复杂调度再看外控 |
| 对焦包围、焦点堆栈 | 原生 FOCUS BKT 可拍序列；外部软件可合成 | 拍序列已有；机内自动合成是另一个功能，不能混淆 |
| 延时摄影/曝光平滑 | 原生 interval timer 与 exposure smoothing | 已有基础；复杂脚本优先外控 |
| 配方库与备份管理 | C1–C7、官方/第三方备份格式、fffw 的 ffbak 研究 | 外部管理有希望；任意参数与机内无限配方并未实现 |
| SD 卡 recipe 导入/导出 | 其他机型有新社区研究；需要文件解析、UI、持久化 | 中期机内候选；X-T4 没有已验证补丁 |
| 按键、Fn、拨轮行为 | 原生可分配功能；FujiHack 旧机先例；XT4 UI/key 命名 | 超出原生选项的映射适合小目标逆向；仍需稳定 hook |
| 自定义快捷菜单、工作流切换 | UI event、菜单、设置结构线索丰富 | 中期候选；不能只改文本或枚举值 |
| 画幅框线、水平辅助、状态文字 | framebuffer/UI 渲染研究有先例 | 适合第一类机内显示实验；overlay 不等于照片裁切 |
| 变形镜头 de-squeeze 预览 | FujiHack 有请求，显示路径可研究 | 未找到 X-T4 实现；EVF/LCD/HDMI 各路径需分别验证 |
| 直方图、波形图、曝光辅助 | 可先做外部 HDMI/预览分析；机内需取得正确图像数据 | 外部可先验证；机内实时性能/数据源未知 |
| 自定义色调曲线、胶片参数 | 现有模拟设置与代码；近期 X-T3 作者移植报告 | 有研究价值；UI、色彩表、ISP 调用、RAW/JPEG/视频路径要同时校验 |
| Reala Ace / Nostalgic Neg 等跨代模拟 | 可能涉及算法/表/专用处理差异 | 不能从菜单名或同品牌推断可移植，更不是改名称即可 |
| 录像时长、码率、模式限制 | 本文件有码率字段线索；旧机有时长补丁先例 | 高不确定性；存储吞吐、编码器、温度和停止流程都必须验证 |
| clean HDMI / 10-bit 输出 | X-T4 原生已有 HDMI 4:2:2 10-bit，内部 H.265 10-bit/最高 400Mbps | 先区分现成功能；不能把它们列为 hack 新增成果 |
| 陀螺仪日志 / Gyroflow | 旧机读传感器先例；IBIS 机型有相关数据源可能 | 先查可读源、时间同步、采样率和记录开销；请求贴不等于已有实现 |
| RAW video / ProRes / 新 codec | 涉及 sensor、ISP、专用编码器、数据总线 | 本轮无 X-T4 可交付证据；不列近期目标 |
| 更高分辨率、帧率或超规格读出 | 受传感器与专用硬件约束 | 没有证据是隐藏开关；不能仅靠固件修改作保证 |
| 新一代 AI 对焦、显著增强 IBIS | 跨核/协处理器/模型/传感器/校准链路 | 极高不确定性；不适合作为首个项目 |
| 调试日志、RAM 中临时运行代码 | fffw ff80 服务接口研究、旧机 USB runner | 值得作为后续研究入口；本轮未验证 X-T4 的具体能力，未操作服务模式 |

原生功能依据：[拍摄设置手册](https://app.fujifilm-dsc.com/en/manual/x-t4/menu_shooting/shooting_setting/index.html)、[包围手册](https://fujifilm-dsc.com/en/manual/x-t4/taking_photo/bracketing/index.html)、[视频设置手册](https://fujifilm-dsc.com/en/manual/x-t4/menu_shooting/movie_setting/)。

[官方 Camera Control SDK](https://www.fujifilm-x.com/en-us/camera-control-sdk/) 明列 X-T4，提供基本遥控和自动传图，支持 USB/TCP-IP 及多个 OS；不提供 RAF 转换信息。该页明确列出个人使用 SDK 连接/控制相机可能使其有限产品保修失效的条款，不能把官方接口说成没有任何实际限制。libfuji/furble 的相关支持也必须对具体机型与操作验证，不在本轮安装或运行相机控制。
